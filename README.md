# GradVPN

Самодельная система управления VPN-инфраструктурой. Не панель типа Marzban или 3X-UI — своя минималистичная замена, потому что панели тяжело автоматизировать и тяжело менять, когда нужно что-то нестандартное.

## Идея

Панели — это фронтенд над JSON-конфигами sing-box. Раз so, можно выкинуть панель и генерировать эти конфиги напрямую: одна база данных как источник истины, и демон на каждом воркере, который раз в минуту сверяется с мастером и сам себя перенастраивает. Никакого ручного SSH на каждый сервер при добавлении пользователя.

## Из чего состоит

Три независимых процесса, никакого общего рантайма:

**vpn-core** (Rust, `vpn-core/`) — единственный компонент с состоянием. HTTP API на axum, слушает `:8443`, всё хранит в PostgreSQL. Бот и воркеры ходят сюда за всем: создать пользователя, отдать конфиг, подтвердить оплату.

**bot** (Go, `bot/`) — телеграм-бот. Обрабатывает `/start`, `/info`, принимает "Я оплатил" от пользователя и шлёт админу карточку с кнопками Подтвердить/Отклонить. Сам бот ничего не хранит — просто прокси между Телеграмом и vpn-core.

**nup** (Go, `nup/`) — демон, который живёт на воркере (не в контейнере, а прямо на хосте). Раз в минуту стучится в vpn-core за списком пользователей, собирает под него `config.json` для sing-box, перезаписывает файл, перезапускает контейнер sing-box через `podman restart`, и накладывает `tc`-лимиты на бесплатных/просроченных пользователей.

Плюс PostgreSQL — таблицы `users`, `nodes`, `payment_requests` (`db/init.sql`), и сам sing-box — крутится в контейнере, конфиг ему пишет `nup`.

## Как это работает вместе

1. Пользователь пишет боту `/start` → бот стучится в vpn-core → создаётся запись в `users` с тарифом `free`.
2. `nup` на воркере каждую минуту дёргает `GET /api/v1/nup/config` с Bearer-токеном узла (`join_token`), получает актуальный список пользователей, перегенерирует конфиг sing-box под свой тип узла (`reality` / `web` / `relay`) и перезапускает контейнер, если конфиг изменился.
3. Пользователь жмёт "Я оплатил" → бот шлёт админу инлайн-карточку → админ жмёт "Подтвердить" → бот вызывает `POST /api/v1/payments/{id}/approve` → vpn-core продлевает `expire_at` и переключает тариф на `premium`.
4. На следующем цикле `nup` увидит новый тариф и снимет с пользователя `tc`-троттлинг.
5. Клиент подключается по ссылке `GET /api/sub/{tg_id}` — vpn-core отдаёт base64 со всеми `vless://`/`hy2://`/`tuic://` конфигами по всем активным узлам.

Обновление конфигов — pull, а не push: воркер сам приходит к мастеру, мастер никуда не стучится. Из-за этого мастеру не нужен SSH-доступ к воркерам и не нужно ничего знать про их сетевую доступность заранее.

## Монетизация

Freemium. У бесплатных пользователей трафик в sing-box идёт через отдельный outbound с `routing_mark`, и `nup` на основании этого маркера накладывает `tc`-лимит (сейчас — жёсткий потолок в 512 Кбит/с). Достаточно, чтобы не смотреть видео, но чтобы зайти в телеграм — хватает.

Платежи не через API банка или ЮKassa — всё вручную: пользователь пишет боту "Я оплатил", админ смотрит на реальный перевод и жмёт кнопку. Никакой автоматической сверки, зато не нужно возиться с эквайрингом.

## API vpn-core

Всё, кроме `/api/sub/{tg_id}`, требует заголовок `Authorization: Bearer <token>`. Для эндпоинтов бота — это `BOT_SECRET` (общий секрет бот↔мастер). Для `/api/v1/nup/config` — это `join_token` конкретного узла, который выдаётся при регистрации узла и хранится в таблице `nodes`.

| Метод | Путь | Кто вызывает | Действие |
|---|---|---|---|
| POST | `/api/v1/users` | бот | создать/продлить пользователя (upsert по `tg_id`) |
| GET | `/api/v1/users/{tg_id}` | бот | получить тариф и креды пользователя |
| DELETE | `/api/v1/users/{tg_id}` | бот | удалить пользователя |
| POST | `/api/v1/payments/{id}/approve` | бот (от админа) | подтвердить оплату, продлить `expire_at`, включить `premium` |
| POST | `/api/v1/payments/{id}/reject` | бот (от админа) | отклонить заявку |
| POST | `/api/v1/nodes` | бот/админ | зарегистрировать узел, сгенерировать `join_token` |
| DELETE | `/api/v1/nodes/{id}` | бот/админ | удалить узел |
| GET | `/api/v1/nup/config` | `nup` (Bearer `join_token`) | pull актуального конфига для своего узла |
| GET | `/api/sub/{tg_id}` | клиент (без авторизации) | base64-список ссылок для VPN-клиента |

## Типы воркеров

`nup` собирает разный `config.json` в зависимости от `node_type` узла в БД:

- **reality** — прямой воркер. VLESS+TCP+XTLS-Vision+Reality на 443, плюс Hysteria2 и TUIC поверх UDP.
- **web** — воркер за веб-сервером: VLESS+httpupgrade и Naive поверх HTTP(S)-путей, плюс те же UDP-протоколы.
- **relay** — не выходит в интернет сам, а проксирует трафик клиентов на другой (upstream) воркер. Нужен там, где напрямую до воркера не достучаться (например, часть мобильных операторов блокирует известные диапазоны адресов).

Примеры сырых конфигов sing-box для каждого типа — в `singbox_examples/`.

## Запуск локально

Всё поднимается одним скриптом:

```bash
./start-services.sh
```

Он поднимает Postgres и тестовый sing-box в подах через `podman-compose` (`compose.yaml`), прописывает тестовый узел в БД, собирает и стартует `vpn-core`, дожидается, пока порт `8443` откликнется, и только после этого поднимает `bot` и `nup`. Порядок важен — оба Go-сервиса падают, если мастер ещё не поднялся.

Нужен `.env` в корне (переменные: `DATABASE_URL`, `TELEGRAM_BOT_TOKEN`, `ADMIN_TG_ID`, `MASTER_URL`, `BOT_SECRET`, `NODE_JOIN_TOKEN`, `NODE_ID`).

## Состояние проекта

MVP, крутится локально в podman-контейнерах для симуляции распределённой топологии. Тестов нет. Автоматизированного деплоя на реальные VPS нет — план по этому есть в `ops.md`.
