# Архитектура

Самодельная система управления VPN-инфраструктурой. Не панель типа Marzban или 3X-UI — минималистичная замена, потому что панели тяжело автоматизировать и тяжело менять, когда нужно что-то нестандартное.

## Идея

Панели — это фронтенд над JSON-конфигами sing-box. Если так, можно выкинуть панель и генерировать эти конфиги напрямую: одна база данных как источник истины, и демон на каждом воркере, который периодически сверяется с мастером и сам себя перенастраивает. Никакого ручного SSH на каждый сервер при добавлении пользователя.

## Из чего состоит

Три независимых процесса, никакого общего рантайма:

**vpn-core** (Rust, `vpn-core/`) — единственный компонент с состоянием. HTTP API на axum, слушает `127.0.0.1:8443`, всё хранит в PostgreSQL. Наружу порт не смотрит: перед мастером стоит Caddy, который терминирует TLS (ACME/Let's Encrypt) на 443 и проксирует на `127.0.0.1:8443`. Бот и воркеры ходят на `https://<домен мастера>` — без порта. Бот и воркеры ходят сюда за всем: создать пользователя, отдать конфиг, подтвердить оплату.

**bot** (Go, `bot/`) — телеграм-бот. Обрабатывает `/start`, `/info`, принимает "Я оплатил" от пользователя и шлёт админу карточку с кнопками Подтвердить/Отклонить. Сам бот ничего не хранит — просто прокси между Телеграмом и vpn-core.

**nup** (Go, `nup/`) — демон, который живёт на воркере (не в контейнере, а прямо на хосте). Раз в минуту стучится в vpn-core за списком пользователей, собирает под него `config.json` для sing-box, перезаписывает файл, перезапускает контейнер sing-box (`podman restart`, `docker restart` как fallback), и накладывает `tc`-лимиты на бесплатных/просроченных пользователей.

Плюс PostgreSQL — таблицы `users`, `nodes`, `payment_requests` (`vpn-core/migrations/`, накатываются автоматически через `sqlx::migrate!` при старте vpn-core), и сам sing-box — крутится в контейнере, конфиг ему пишет `nup`.

## Как это работает вместе

1. Пользователь пишет боту `/start` → бот стучится в vpn-core → создаётся запись в `users` с тарифом `free`.
2. `nup` на воркере каждую минуту дёргает `GET /api/v1/nup/config` с Bearer-токеном узла (`join_token`), получает актуальный список пользователей, перегенерирует конфиг sing-box под свой тип узла (`reality` / `web` / `relay`) и перезапускает контейнер, если конфиг изменился.
3. Пользователь жмёт "Я оплатил" → бот шлёт админу инлайн-карточку → админ жмёт "Подтвердить" → бот вызывает `POST /api/v1/payments/{id}/approve` → vpn-core продлевает `expire_at` и переключает тариф на `premium`.
4. На следующем цикле `nup` увидит новый тариф и снимет с пользователя `tc`-троттлинг.
5. Клиент подключается по ссылке `GET /api/sub/{tg_id}` — vpn-core отдаёт base64 со всеми `vless://`/`hy2://`/`tuic://` конфигами по всем активным узлам.

## Pull, а не push

Обновление конфигов — воркер сам приходит к мастеру, мастер никуда не стучится. Из-за этого мастеру не нужен SSH-доступ к воркерам и не нужно ничего знать про их сетевую доступность заранее.

Это архитектурное ограничение, а не деталь реализации: если появляется потребность в срочном уведомлении воркера (например, новый пользователь должен получить доступ быстрее следующего опроса) — решение всегда через более частый опрос или через push данных снизу вверх (воркер сам отправляет), а не через открытие входящего порта на воркере.

## Владение приватным ключом Reality

Только у `nup` есть доступ к бинарнику sing-box для генерации Reality-keypair, поэтому именно `nup` — а не мастер — генерирует и хранит приватный ключ (локально, путь задаётся `NUP_REALITY_KEY_PATH`, никуда не отправляется). На мастер уходит только публичная часть — `public_key` и `short_id` — через `POST /api/v1/nup/node-keys` (см. `docs/dev/api.md`). Мастер сохраняет их в таблице `nodes` по `join_token` и отдаёт `relay`-узлам, которым нужно достучаться до этого узла как до upstream.

Ключ генерируется один раз при первом запуске `nup` на узле (`nup/reality.go::EnsureRealityLocalKeys`) и переиспользуется при последующих запусках/тиках — генерация не привязана к регистрации новых пользователей.

## Типы воркеров

`nup` собирает разный `config.json` в зависимости от `node_type` узла в БД (см. `nup/template.go`):

- **reality** — прямой воркер. VLESS+TCP+XTLS-Vision+Reality на 443, плюс Hysteria2 и TUIC поверх UDP.
- **web** — воркер за веб-сервером: VLESS+httpupgrade и Naive поверх HTTP(S)-путей, плюс те же UDP-протоколы.
- **relay** — не выходит в интернет сам, а проксирует трафик клиентов на другой (upstream) воркер. Нужен там, где напрямую до воркера не достучаться (например, часть мобильных операторов блокирует известные диапазоны адресов). Держит собственный Reality-inbound (свой независимый keypair) и одновременно выступает клиентом Reality к upstream-узлу, используя его публичный ключ.

Примеры сырых конфигов sing-box для каждого типа — в `singbox_examples/`.

## Монетизация

Freemium. У бесплатных пользователей трафик в sing-box идёт через отдельный outbound с `routing_mark`, и `nup` на основании этого маркера накладывает `tc`-лимит (сейчас — жёсткий потолок в 512 Кбит/с). Достаточно, чтобы не смотреть видео, но чтобы зайти в телеграм — хватает.

Платежи не через API банка или ЮKassa — всё вручную: пользователь пишет боту "Я оплатил", админ смотрит на реальный перевод и жмёт кнопку. Никакой автоматической сверки, зато не нужно возиться с эквайрингом.
