# Форк созрел раньше чем планировалось

## История зарождения идеи форка проекта

После успешного ручного end-to-end тестирования и проверки работоспособности кластера grudv, обнаружились некоторые факты которые служат мотивацией для форка еще до начала CD.

LTE блокировки работают в режиме Default Deny, то есть доступ сохраняется только до узкой части сети. Сообщество собрало 2 основных и еще актуальных способа борьбы с этим режимом:

1. Маскировка подключения под легитимные TURN звонки. (openlibrecommunity olcRTC by zarazaex) — в текущий форк не входит, вынесено в план на будущее развитие: интеграция olcRTC — трудоёмкий процесс, требует отдельной проработки.
2. XHTTP + Vless + Reality + фрагментация пакетов в режиме xhttp up, с ограничением до 16Кб размера пакетов (после этого идет дроп соединения со стороны ТСПУ поэтому задача фрагментации не давать этому случиться) решение было получено от команды DurevVPN
3. QUIC протоколы остаются эффективными в домашних сетях, поэтому TUIC и Hysteria 2 в форк перекачуют

## Текущее состояние проекта

Проект готов к запуску, в файле /home/leont/dev/vpn/personal/extras_plan.md описан большой фронт работы, но ядерную логику проекта он практически не затрагивает. Существующие незакрытые пункты подробно описаны в /home/leont/dev/vpn/personal/future-improvement.md, тем не менее они терпят внедрения уже после запуска проекта.

На данный момент проект постулирует 3 вида воркеров:

1. Reality воркер
2. WebServer воркер
3. Relay воркер

Примеры их конфигураций, смысл и логику их генерации можно найти в фалах nup и vpn_core.

## Предполагаемые изменения для форка

1. Оставить 1 тип воркера а именно reality, но изменить его архитектурно (глобальные изменения в nup)

    1. 443/tcp порт отдается xray-core(вместо sing-box) под связку XHTTP + Vless + Reality + фрагментация пакетов в режиме xhttp up, с ограничением до 16Кб размера пакетов
    2. 443/udp отдается под Caddy который будет заниматься демультипликацией hysteria 2 и tuic транспорта. для обоих протоколов реализована функция прыжка по портам. (это не финальная концепция, может оказаться так, что для эффективной работы xhttp нужен и udp порт, этот момент требует уточнения в документации)

        **ИССЛЕДОВАНО (2026-07-24): подход не рабочий, план требует пересмотра.**

        - Голый Caddy UDP-демультиплексией не занимается вообще — эта функция есть только в стороннем плагине `caddy-l4` (mholt/caddy-l4), а не в ядре Caddy.
        - `caddy-l4` сам помечен как нестабильный ("still in development, expect breaking changes"), и по практическим отчётам (github.com/mholt/caddy-l4 issue #348) UDP-роутинг с публичного интернета на реальном сервере у пользователей не заработал — это не проверенное в бою решение.
        - Even если бы `caddy-l4` работал стабильно: и Hysteria2, и TUIC умеют маскироваться под HTTP/3 с одинаковым ALPN `h3` (стандартная техника обфускации против DPI для обоих). Если оба сконфигурированы с одинаковым ALPN — а это обычная практика ради устойчивости к блокировкам — Caddy технически не может различить потоки по ALPN/SNI, единственному признаку, видимому на layer4 до расшифровки.
        - Запасной вариант "sing-box mixed-listener" тоже не подходит: запрос на несколько разных inbound-протоколов на одном порту в sing-box был закрыт мейнтейнерами как "not planned" (github.com/SagerNet/sing-box issue #559). Каждый inbound в sing-box требует собственный порт.

        **Вывод:** Hysteria2 и TUIC на форке не могут делить один UDP-порт через Caddy — Caddy из плана исключается, порт 443/udp под общий демультиплексор не отдаётся.

        **Принятое решение (2026-07-24):** протоколы разводятся по отдельным портам, как и было до форка, без демультиплексора на 443/udp:

        - Hysteria2 и TUIC слушают статичные порты (Hysteria2 — 8443/udp, как в оригинальной схеме, без изменений; TUIC — свой статичный порт).
        - Поверх статичных портов обязательно включается port hopping: снаружи клиент бьёт в случайный порт из выделенного диапазона, iptables/DNAT перебрасывает трафик на реальный статичный listener. Диапазоны непересекающиеся:
          - TUIC: 10000–15000/udp → форвардинг на статичный порт TUIC
          - Hysteria2: 15001–20001/udp → форвардинг на 8443/udp
        - Статичные порты (443/udp, 8443/udp) в теории можно закрыть снаружи, оставив только hopping-диапазоны, но ради надёжности их решено оставить открытыми параллельно.

WebServer и Relay улетают в обсуждение пока проект не будет полноценно запущен с CI/CD.

    Судьба кода WebServer/Relay в форке: решение по ним отложено в обсуждение (см. раздел про relay ниже), код (`buildWebConfig`/`buildRelayConfig` в `nup/template.go`, обработка `node_type`/`upstream_node` в схеме и `vpn-core`) остаётся в форке как есть до того, как обсуждение будет закрыто.

С точки зрения инфраструктуры переход на xray можно реализовать тремя способами:

1. Два конвейера на одном сервере в общем compose: sing-box управляет udp протоколами, а xray дает xhttp и vless.
2. Три контейнера с независимыми бинарниками в одном compose: xray для tcp, официальные контейнеры hysteria 2 и tuic для udp.
3. Переход на mihomo.

**ИССЛЕДОВАНО (2026-07-24):**

Текущая архитектура `nup` (`fetchAndApplyConfig` в `main.go`) — один цикл: получить конфиг с мастера → сгенерировать один `config.json` → сравнить с прошлым → перезаписать → `restart` одного контейнера `sing-box-worker` по имени из `Config.ContainerName`. Переход на 2 или 3 независимых бинарника требует: по одному генератору конфига на бинарник (`GenerateConfig` уже устроен как диспетчер по `node_type`, тот же паттерн можно применить к диспетчеру по бинарнику), отдельного отслеживания изменений и `restart` для каждого контейнера, и переноса `SyncCertificate`/`ApplyTrafficShaping` на актуальные пути сертификатов и routing_mark каждого бинарника — сама структура `nup` это допускает без архитектурной ломки, независимо от выбранного варианта.

**По вариантам:**

1. **Дуплекс sing-box+xray в одном compose.** Референс-проект `aleskxyz/reality-ezpz` уже реализует похожую комбинацию (sing-box/xray + tuic + hysteria2 в docker compose с выбором транспорта), но его README не документирует, как разведены порты между процессами — требует разбора самого скрипта/сгенерированного compose перед тем, как опираться на него как на образец.

2. **Три независимых официальных бинарника.** Готовые официальные образы есть для всех трёх: `teddysun/xray`, `teddysun/hysteria`, и `itsusinn/tuic-server` (активно поддерживаемый форк-преемник оригинального TUIC) — все три получают конфиг конвенциональными форматами (JSON/TOML), что делает программную генерацию из Go несложной; `tuic-server` в частности — плоская TOML-секция `[users] uuid = "password"`, тривиально маппится из уже существующей структуры `MasterUser`.

3. **Переход на mihomo.** Неожиданная находка: mihomo, вопреки первому впечатлению, умеет не только клиентские outbound, но и серверный VLESS-inbound с `RealityConfig`+`XHTTPConfig` — то есть технически способен закрыть xhttp+vless+reality в одном бинарнике. Но здесь же всплыл системный риск уровня выше архитектуры инфраструктуры.

**Критическая находка, касающаяся XHTTP+Reality независимо от выбранного варианта:**

- [XTLS/Xray-core issue #6048](https://github.com/XTLS/Xray-core/issues/6048): VLESS+Reality (и RAW/TCP-Vision, и XHTTP) стабильно работает при подключении mihomo-клиентов, но даёт `failed to read client hello` при подключении официальных Xray-core клиентов (включая vanilla Xray-core, HAPP, INCY) к тем же серверам — воспроизводится на актуальных релизах 2026 года.
- [XTLS/Xray-core issue #6256](https://github.com/XTLS/Xray-core/issues/6256): в версии 26.3.27 Reality сам генерирует раздутый ClientHello (~1892 байта против ~500-700 у 26.3.23), из-за чего ClientHello фрагментируется на уровне TCP/MTU ещё до применения запланированной в форке фрагментации — и эта непреднамеренная фрагментация обрывает соединение на некоторых DPI. Единственный задокументированный воркэраунд — откат на 26.3.23; фикса нет.

Это прямо бьёт по цели раздела 29 документа (фрагментация до 16Кб именно для того, чтобы не давать ТСПУ дропать соединение) — баг производит противоположный эффект ещё до применения намеренной фрагментации. Перед фиксацией любого варианта нужно: (а) зафиксировать конкретную версию Xray-core, не подверженную #6256, (б) проверить #6048 на актуальность для выбранной пары сервер/клиент вручную, вживую, а не полагаясь на клиентскую совместимость "в теории".

**Совместимость с клиентами (уточнено пользователем, приоритетнее моих исходных находок ниже):** на Arch Linux в текущей эксплуатации NekoBox стабильно поддерживает XHTTP. Основной мобильный клиент для конечных пользователей — Karing (доступен и как desktop-клиент) — подтверждено кроссплатформенный (iOS/Android/Windows/macOS/Linux/tvOS), на базе sing-box, заявлена поддержка vless+xhttp+reality; в issue-трекере (`KaringX/karing` #1400, #441) есть открытые баги именно по связке vless+xhttp+reality на Android/Windows, но они активно чинятся мейнтейнерами — не блокер, но стоит проверять актуальный релиз перед раскаткой.

Мой более ранний вывод про NekoBox (открытый feature request #1087 на XHTTP, отсутствие нативной поддержки) — устарел или относился не к той версии/платформе; фактическая эксплуатация показывает обратное. Это не отменяет остальные находки этого раздела (#6048, #6256 по Xray-core серверу), но снимает NekoBox/Karing как источник риска по совместимости клиентов.

**ПРИНЯТОЕ РЕШЕНИЕ (2026-07-24): вариант 2 — три независимых официальных бинарника.**

xray-core (443/tcp, xhttp+vless+reality) + `teddysun/hysteria` (8443/udp, статичный порт) + `itsusinn/tuic-server` (свой статичный порт) — все три в собственных контейнерах, каждый со своим готовым официальным образом. Порт hopping (TUIC 10000–15000/udp, Hysteria2 15001–20001/udp через iptables/DNAT, см. выше) применяется поверх этой схемы независимо от того, какой бинарник реально слушает статичный порт.

Причина выбора именно этого варианта: быстрее всего в реализации — не нужно ни разбирать чужой скрипт `aleskxyz/reality-ezpz`, чтобы понять, как он разводит порты между sing-box и xray в дуплексе (вариант 1), ни осваивать новый движок mihomo (вариант 3, при том что mihomo подвержённость #6048/#6256 не проверена). Официальные образы `teddysun/xray`, `teddysun/hysteria`, `itsusinn/tuic-server` конфигурируются простыми форматами (JSON/TOML), что укладывается в уже существующий паттерн `nup` — диспетчер по бинарнику вместо диспетчера по `node_type`, три независимых `GenerateConfig`-подобных генератора, три отдельных `restart` по имени контейнера.

**Осознанно принятый риск:** #6048 и #6256 (см. выше) не проверялись живьём и проверяться не будут до e2e-тестирования — это сознательное решение ради скорости проработки реализации, а не пробел в анализе. Если баги подтвердятся на выбранной версии Xray-core в ходе e2e, потребуется либо пин на версию до 26.3.27, либо пересмотр варианта 2 в пользу mihomo как xray-совместимой замены именно для tcp-компонента (443/tcp), без переработки hysteria2/tuic-частей схемы.

В любом случае форк меняет логику работы nup.

## Анализ кодовой базы под реализацию (2026-07-25)

Копия проекта для форка создана как отдельный git-репозиторий: `/home/leont/dev/vpn-fork` (клон текущей истории, `origin` отвязан). Дальнейшая разработка форка ведётся там, этот документ (`docs/dev/fork-logic.md`) остаётся источником решений в исходном репозитории.

**Объём кода, который трогает форк:** `nup` — 976 строк Go, `vpn-core` — 893 строки Rust. Компактно.

- **`nup/template.go` (437 строк)** — главная точка изменений. Паттерн у всех трёх текущих builder-функций одинаковый: JSON-шаблон строкой → `json.Unmarshal` в `map[string]any` → точечная подстановка пользователей/ключей по индексам массива → `json.MarshalIndent`. Форк должен воспроизвести этот же паттерн для трёх новых генераторов (xray JSON, hysteria2 YAML, tuic TOML) вместо трёх текущих (reality/web/relay под sing-box).
  - Хардкод, который придётся трогать: `server_name: "telemetry.mozilla.org"` (Reality camouflage-хост) и порты `443`/`8443` зашиты прямо в JSON-строку шаблона, не вынесены в `Config`/env. Это значение **задублировано** в `vpn-core/src/handlers.rs:33` (`const REALITY_SNI`, используется в `build_sub_configs` для генерации клиентских subscription-ссылок) — при смене camouflage-хоста нужно менять оба места синхронно, иначе ссылки, которые бот отдаёт пользователям, разъедутся с тем, что реально проверяет сервер при хендшейке.
  - `buildWebConfig`/`buildRelayConfig` — решение отложено в обсуждение (см. выше), код не трогается.

- **`nup/main.go`** — `fetchAndApplyConfig` сейчас: один HTTP-запрос к мастеру → один `GenerateConfig` → один `config.json` → один `restart` контейнера `sing-box-worker`. Под вариант "3 бинарника" нужно продублировать тройку (генератор, путь конфига, имя контейнера) — `Config` уже параметризован путями/именами, требуется добавить поля (`XrayConfigPath`, `Hy2ConfigPath`, `TuicConfigPath`, три `ContainerName`) и обернуть тело функции в перебор трёх сущностей.

- **`nup/reality.go`** — почти не меняется. Единственная точка контакта с бинарником — `exec.Command("sing-box", "generate", "reality-keypair")` (строка 63), заменяется на `xray x25519`; формат ключей идентичен (см. решение выше), остальной файл (хранение, push на мастер, `setRealityKeys`) не трогается.

- **`nup/utils.go`** — `SyncCertificate` сейчас копирует сертификат в один путь (`/etc/sing-box/{fullchain,privkey}.pem`). При трёх бинарниках с разными путями конфигов нужно копирование в три места (см. `examples/xray-config.json`, `examples/hysteria2-config.yaml`, `examples/tuic-config.toml` в форке — у каждого свой ожидаемый путь к сертификату). `ApplyTrafficShaping` (tc + `routing_mark`) не меняется — работает на уровне интерфейса, не привязана к бинарнику.

- **`vpn-core`** — минимальные изменения: `models.rs`/`db.rs`/`0001_init.sql` не требуют новых полей (данные пользователей общие для всех протоколов). Единственная содержательная правка — `handlers.rs:build_sub_configs` (строка 45): `type=tcp&flow=xtls-rprx-vision` в клиентской vless-ссылке меняется на XHTTP-эквивалент при переходе на новый транспорт.

- **Тесты** — `nup/template_test.go` жёстко завязан на структуру sing-box JSON и на все три `node_type`; `TestGenerateConfigWeb`/`TestGenerateConfigRelay*` удаляются вместе с кодом, `TestGenerateConfigReality` переписывается под новый формат — сам подход (декодировать сгенерированный конфиг и проверять состав пользователей/маршрутов) стоит сохранить и применить к каждому из трёх новых генераторов отдельно.

- **`vpn-core/db/dev-up.sh`** — единственный существующий shell-скрипт в репозитории, чисто dev-тулинг для локального Postgres (не тронут схему БД), форка не касается.

### `examples/` в форке (2026-07-25)

В `/home/leont/dev/vpn-fork/examples/` собраны черновые (не запускавшиеся) шаблоны под архитектуру "3 бинарника": `compose.yaml` (три контейнера, `network_mode: host`, `CAP_NET_ADMIN` для routing_mark — по образцу текущего `personal/singbox-compose.yaml`), `xray-config.json` (VLESS+XHTTP `mode: packet-up`+Reality на 443/tcp, `scMaxEachPostBytes: 16384` под требование фрагментации до 16Кб), `hysteria2-config.yaml` (статичный 8443/udp), `tuic-config.toml` (статичный 8444/udp).
