# Известные проблемы

## Открыто: relay не аутентифицируется на upstream-узле

`buildRelayConfig` (`nup/template.go:429-434`) прописывает в оба VLESS-outbound константу `<FOREIGN_VLESS_UUID>`, а в оба Hysteria2-outbound — `<FOREIGN_HY2_PASSWORD>`. Это буквальные строки-заглушки, которые никогда ничем не заменяются — авторизация на upstream-узле провалится для всех клиентов `relay`-узла.

**Почему это в принципе не может работать как есть:** relay — посредник: принимает подключения на своём Reality-inbound и перенаправляет трафик на upstream-узел, где сам выступает клиентом VLESS/Hysteria2. На upstream-узле нет отдельного пользователя "relay" — есть только обычные пользователи мастера, каждый со своим `vless_uuid`/`hy2_password` (таблица `users`). Чтобы upstream принял трафик конкретного клиента, `relay` должен подключаться с UUID/паролем именно этого клиента — общей учётки быть не может в принципе.

**Форма исправления:** не один общий outbound на всех, а per-connection сопоставление "клиент relay → его личные креды на upstream" — через sing-box `users`/детект по `inbound`-пользователю на relay и проброс тех же значений, под которыми этот пользователь уже заведён на upstream. Данные для этого уже приходят с мастера в `MasterConfigResponse.Users` (`nup/template.go`) — просто сейчас не используются в блоке outbound.

Reality-ключи (приватный/публичный/short_id) для relay уже работают корректно (см. `docs/dev/architecture.md` → "Владение приватным ключом Reality") — это отдельная, уже решённая часть той же конфигурации.

## Закрыто: обмен Reality-ключами между nup и мастером

Было: мастер хранил колонки `reality_pub_key`/`reality_short_id`, но их никто не заполнял; `nup` зашивал в конфиг заглушки `<REALITY_PRIVATE_KEY>`/`<REALITY_SHORT_ID>`, никогда их не заменяя. Исправлено — см. `docs/dev/architecture.md` → "Владение приватным ключом Reality" и `docs/dev/api.md` → `POST /api/v1/nup/node-keys`.
